# Ironlog — Adversarial Review (2026-09-16)

Full read-only audit of the app at v0.51.0, across four dimensions (engine correctness, data/sync/storage, UI/interaction, performance) plus a product-gap pass. Nothing was changed. Findings are ranked, tagged **CONFIRMED** (code traced or reproduced) or **SUSPECTED**, with file:line, a concrete failure, and a fix.

## The one-paragraph summary

The app is fundamentally sound: the import/sync layer is genuinely hardened, the finish-workout path protects data, and the core lifting math is correct. The real weaknesses cluster in **two young feature areas that are only half-wired through the engine** — the *time-held / assisted lift* family (planks, carries, hangs, assist machines) and the *stopwatch* (v0.50.0, which currently has **zero test coverage** and is the least-guarded interaction in the app). Separately, there is one **latent data-loss path** (a workout in progress isn't quota-protected) and a **permanent battery drain** on installed phones. None of this is on fire; several are quick, high-value fixes.

## 1. Engine correctness

**C1 — Bodyweight time-held lifts never get a personal record.** *High · CONFIRMED (reproduced).*
`src/engine/analysis.js:315` — `personalRecords` guards `if(!w||!r)return;` where `w = setLoad(id, st.w, bw)`. For a bodyweight hold `setLoad` is 0 (not in `BW_FACTOR`), so the set is discarded *before* the time-metric branch runs. Verified: a 3×60s plank returns **0 PR rows**; a farmers-carry *with* weight returns 1. So every one of the five new bodyweight holds — the exact lifts the v0.50 stopwatch was built for — can never show a record.
**Fix:** for `TIME_METRIC` ids, admit the set when `r>0` regardless of `w` (the time-metric PR is "longest, then heaviest"). Keep the existing guard for ordinary bodyweight lifts.

**C2 — Assisted lifts are misread as stalled → wrongful rotation.** *Med-High · CONFIRMED (traced).*
`src/engine/builder.js:322` (`isStalled`) treats a lower recent top weight and lower e1RM "score" as a stall — but on `INVERTED_LOAD` lifts, *progress is a lower number* (less assist). A lifter dropping assist 90→75→60 looks stalled, so `planWorkout` swaps the lift out mid-progress.
**Fix:** make `isStalled`/`recentPerfs` inverted-aware (for `INVERTED_LOAD`, "improved" = top weight went *down*).

**C3 — Trend chart & progression stat use a meaningless e1RM for inverted/timed lifts.** *High · CONFIRMED (reproduced).*
`exerciseSeries` (`progression.js:118`), `bestE1rmBefore` (`:136`), `progressionStat` (`analysis.js:52`) call `e1rm(setLoad,…)` with no `INVERTED_LOAD`/`TIME_METRIC` guard (unlike `personalRecords`, which branches correctly). Verified: the assisted-pull-up trend goes **114 → 76 as the user gets stronger** (reads as decline), and the plank trend chart is **empty** (load 0 → nothing plotted). Timed carries feed seconds to Epley, so a lighter-longer carry outranks a heavier one.
*Note:* the live "★ New PR" line and finish summary are already gated for these lifts (v0.49.1); this is the same class of bug in the surfaces that were missed — the trend card and the coach's "N lifts trending up."
**Fix:** in these three helpers, branch on inverted (lower load = better) and time (drop from e1RM entirely; plot seconds or skip).

**C4 — Bodyweight & assisted math is applied retroactively with *today's* bodyweight.** *Med · CONFIRMED (traced).*
`setLoad`/`sessionVolume`/`personalRecords`/`exerciseSeries` always use `bw()` (the current setting) for *every* historical set. Change your bodyweight and all past pull-up / assisted-dip volume and PRs silently shift; an assisted lift's volume is `currentBodyweight − assist` even for a session logged months ago. There's no record of what you weighed then.
**Fix (larger):** store a lightweight bodyweight log and use the value nearest each session's date; or snapshot effective bodyweight onto the set at log time. See G1.

**C5 — `progressionStat` doesn't exclude `nc` ("doesn't count") sets.** *Low-Med · SUSPECTED (not reproduced).*
`analysis.js:52` filters `isWorking` only; every sibling excludes `nc`. A quick 2-session repro returned `{n:0,up:0}` (the function needs more tenure to fire), so the practical impact is unconfirmed — but the guard asymmetry is real and should be closed for consistency.

**C6 — `calcStreak` may drop the one-skip grace at the current-week boundary.** *Low · SUSPECTED.*
`progression.js:333` — if the current week is untrained *and* the prior week is empty, it returns 0 without applying the single-skip tolerance the in-loop logic grants elsewhere. Edge case; worth a targeted test.

**C7 — `deloadStats` load-% is meaningless for assist machines.** *Low · CONFIRMED.* Display-only (Recovery card); never feeds prescriptions.

## 2. Data / sync / storage

The whitelist rebuild in `parseImport` genuinely closes prototype-pollution and HTML-injection, NaN/Infinity are filtered, and the finish path protects the workout. Gaps behind that:

**D1 — A workout *in progress* is not quota-protected → silent loss.** *High · CONFIRMED.*
`store.js:46` (`saveActive`) ignores both `lsSet` return values and `persistActive` (`:93`) never checks them. The active workout lives **only** in `il_active` until Finish. If storage fills mid-session, every set-edit's save fails silently, `state.storageError` is never set (only `saveSessions` sets it), so there's no banner — and a reload/crash loses the whole session. The finish path handles quota correctly; this is the one write path holding the *sole* copy of live data that doesn't.
**Fix:** have `persistActive` check the return and set `state.storageError` / warn, mirroring `commitFinish`.

**D2 — Artifact backend never propagates deletions.** *Med-High (High for artifact users) · CONFIRMED.*
`store.js:164` builds `remote` only from docs that exist and calls `mergeSessions`, which can add/update but never remove; there's no shared tombstone doc (unlike the Dropbox file's `deleted` map). Delete on device B → device A keeps its copy forever, and if A touches it, `pushSession` re-creates the doc and *undoes* the delete on B. (`const t=applyTombstones(...,{})` at `:166` is computed and discarded — dead code confirming the tomb never crosses.)
**Fix:** persist tombstones as a doc in the artifact DB and apply them in the snapshot handler.

**D3 — `updatedAt` ties & clock skew cause silent divergence / lost edits.** *Med · CONFIRMED (tie) / inherent (skew).*
`sync.js:38`, `resolveActive:119`. An exact `updatedAt` tie between two differing versions keeps local and never reconciles; a device with a fast clock can overwrite a genuinely newer edit. This is the riskiest *untested* integrity contract.

**D4 — Two devices each mid-workout: one active session is silently discarded.** *Med · CONFIRMED.* `resolveActive` keeps the newer `updatedAt` and drops the other; its logged sets never reached the blob, so they're gone.

**D5 — Import silently truncates history at 2000 sessions.** *Med · CONFIRMED.* `sync.js:74` `MAX_ARR=2000`; `exportPayload` writes all, re-import drops the oldest beyond 2000 with no warning (~5.5 years of daily logging).

**D6 — `deleted` / `seen` maps have no key-count cap.** *Med · CONFIRMED.* `cleanDeleted`/`cleanSeen` iterate all keys with no `.slice`; a corrupt backup with a huge `deleted` map is accepted, persisted, and re-uploaded every sync.

**D7 — Manual import & artifact snapshots bypass the "newer-version" gate.** *Med · CONFIRMED (latent).* The version latch exists only in `dropboxAdapter.syncNow`; harmless while `SCHEMA=1`, a real hazard the moment schema 2 ships (and there's no migration logic yet, only a schema stamp).

**D8 — Non-blob writes ignore quota; `unmarkSets` upserts inside a loop.** *Med/Low · CONFIRMED.* `upsertSession` checks `saveSessions` but then calls `saveDirty()` unchecked (a saved session may never be marked for cloud push). `unmarkSets` (`ui-bind.js:159`) calls `upsertSession` inside a `forEach` over all sessions — several full-blob serializes + cloud pushes for one tap.

**D9 (Low) — Dropbox residuals:** refresh token in localStorage (CSP-mitigated); disconnect-on-401 leaves stale "connected" UI; no OAuth `state` param; `?code` stripped before the token exchange (a network blip forces re-login). `esc()` doesn't escape single quotes (safe only because every attribute uses double quotes — an unstated invariant).

## 3. UI / interaction

Recurring theme: **the stopwatch is the least-guarded interaction and has no tests.** The duplicate-function-name hazard is currently clean.

**U1 — Stopwatch caches a stale exercise index.** *High · CONFIRMED.*
`ui-bind.js:500/520`. `swState.ei` is captured at start and never revalidated. Delete or auto-reorder an exercise while it runs, then Stop → it reads `t.exercises[ei]`, which is now a different lift or `undefined` (the hold is silently discarded). Everywhere else reads `ei` fresh from the clicked element for exactly this reason.
**Fix:** capture the exercise `id` (or object ref), not the index; resolve it at Stop.

**U2 — Rest timer and stopwatch can show at once.** *Med · CONFIRMED.* `startStopwatch` calls `stopRest()`, but `startRest()` doesn't `stopSw()`. With auto-rest on, ticking a set while a plank stopwatch runs stacks both fixed bars in the same slot. **Fix:** `startRest` should `stopSw()`.

**U3 — Leaving the editor orphans the stopwatch.** *Med · CONFIRMED.* `stopSw()` is only called from finish/discard. Tap **Home** (or switch tabs) mid-hold → `#swbar` keeps counting over Home/History/Progress, and Stop still writes into the (now-hidden) active workout. `tickSw` never checks the current screen (unlike the cardio clock, which self-stops). **Fix:** stop the stopwatch on the active→inactive transition (or self-stop in `tickSw` when not on the active editor).

**U4 — Stopwatch writes its hold into a warm-up set.** *Med · CONFIRMED.* `ui-bind.js:526` `find(s=>!s.done)` ignores `warm`. If the next open set is a warm-up, the real hold lands there and is ticked → excluded from PRs/volume. **Fix:** skip warm sets when picking the target.

**U5 — Manually ticking a timed set with no seconds is accepted, then dropped at Finish.** *Low · CONFIRMED.* The weight-nudge is exempted for `TIME_METRIC`, so a plank set with empty reps ticks done; `finalizeSets` then drops it (`r>0` required) with no warning. **Fix:** for timed lifts, require seconds before ticking (mirror the weight nudge).

**U6 — `parseWeightInput` accepts multiple dots; a typed `0` is stored as the string `"0"`.** *Low · CONFIRMED.* `"12.5.5"` displays as-is while `st.w` stores `12.5` (visible/stored mismatch). No crash.

**U7 — Timers have no `aria-live`.** *Low.* VoiceOver users get no readout of the rest/stopwatch countdown. Icon buttons elsewhere are labelled well; this is the gap.

## 4. Performance & scaling

No memoization anywhere; every derived stat is a full-history scan recomputed per render. Sizing: ~2 KB/session → 1k ≈ 1.8 MB, 5k ≈ 9 MB.

**P1 — Always-on rAF loop writes DOM every frame forever.** *High (installed PWA) · CONFIRMED.* `ui-views.js:451` runs ~60×/s for the life of the app; in standalone mode `syncViewportDeficit` writes `--screen-h`/`minHeight` every frame *before* its early-out. Permanent main-thread churn and battery drain. **Fix:** run the loop only until the launch-time viewport deficit stabilizes (~2s), then stop and rely on the already-registered resize/scroll/visibility listeners; guard the per-frame writes.

**P2 — Progress tab = ~8 full-history scans per render, none shared; editor fully rebuilds on every tick.** *High @ scale · CONFIRMED.* One Progress render runs `personalRecords` twice, `analyze` ~3×, plus `weeklyVolumes`/`muscleSetCounts`/`deloadStats`/`timeTrends`/`cardioStats` — and *every collapse-toggle and cloud ping re-renders the whole tab*. Separately, every set tick rebuilds `#view` and recomputes `bestE1rmBefore` (a full `real()` scan, no early exit) for **every** exercise card. At 2k sessions an 8-exercise workout does ~380k set-iterations per checkbox tap. **Fix:** compute a derived-stats bundle once per render (cache keyed by `sessions.length` + max `updatedAt`); patch the changed row in place on a tick instead of a full rebuild; make collapse-toggles mutate the DOM, not `render()`.

**P3 — `real()`/`completed()` allocate a full array on every call.** *Med · CONFIRMED.* Called many times per render → GC pressure at scale. Subsumed by P2's compute-once fix.

**P4 — localStorage is the hard ceiling.** *Med now, High later · CONFIRMED.* At ~2 KB/session the UTF-16 blob hits the ~5 MB cap around **2,000–2,500 sessions**, after which on-device writes silently fail (D1 makes that worse). Boot also `JSON.parse`s the whole blob synchronously (~100–300 ms at 5k). **Fix (architectural):** move sessions to IndexedDB (async, large quota, per-record writes) behind the existing store API. This is the only thing that lets the app truly hold years of history.

**Non-issues (checked):** timers are correctly scoped and torn down (except the rAF loop); `#view` click is delegated once; the live editor persists only the small `il_active` blob per keystroke (the feared multi-MB keystroke serialize does *not* happen); the service worker is network-first for the document (no staleness trap).

**Highest-ROI three:** (1) memoize the derived-stats layer + stop re-rendering tabs on collapse; (2) stop full-rebuilding the editor on every set tick; (3) bound the rAF viewport loop.

## 5. Missing features / product gaps

Present and good: routines, repeat-a-session, edit/delete past sessions, reorder, per-exercise notes, deloads, cardio, stopwatch, PR-adjust, profile, Dropbox/artifact sync, JSON import/export, unit conversion, calendar, coach notes.

Gaps worth considering (roughly by value):

- **G1 — Bodyweight over time.** Only a single current value exists, and it's applied retroactively (C4). A lightweight weigh-in log would fix the correctness issue *and* is a feature users expect. This was flagged earlier as the best low-cost health-tracking win.
- **G2 — Session-level note.** Notes are per-exercise only; there's no "how the whole session felt / slept badly / tweaked back" note.
- **G3 — Edit a past session's *date/time*.** You can edit sets and delete, but not fix a mis-dated strength session (cardio manual entry has back-dating; strength edit doesn't).
- **G4 — Plate / warm-up calculator.** No "what plates make 102.5" or warm-up ramp helper — common asks for barbell work.
- **G5 — Exercise-history search / filter in History.** Calendar + list only; no "show me every squat session."
- **G6 — PR history / timeline.** The PR board shows only the current best; there's no list of *when* PRs were set (the trend shows e1RM, not PR events).
- **G7 — CSV export.** Backup is JSON only; a CSV would let users pull data into a spreadsheet.
- **G8 — Supersets / circuits.** No way to group exercises performed together (may be a deliberate simplicity choice).
- **G9 — Reminders / scheduling.** Notifications exist only for rest; no "you haven't trained legs in 8 days" or session reminders.

## Recommended sequencing

**Batch A — correctness the current features imply (small, high value):**
C1 (plank PRs), C3 (inverted/timed trend + stats), C2 (assisted stall), U1 (stopwatch stale index). These finish wiring the two young feature families through the engine. Add the missing tests the reviews named (the entire stopwatch path; inverted/timed in `exerciseSeries`/`progressionStat`/`bestE1rmBefore`; `personalRecords` for bodyweight holds).

**Batch B — data safety (small–medium):** D1 (protect the in-progress workout), U2/U3/U4 (stopwatch lifecycle), then D2 (artifact deletions) and D6 (cap the maps).

**Batch C — performance (medium):** P1 (bound the rAF loop) is a quick win; P2/P3 (memoize stats, stop rebuilding the editor) are the scaling fixes.

**Batch D — bigger bets (discuss first):** C4/G1 (bodyweight over time), P4 (IndexedDB), and the product features in §5.

None of A–C is large; Batch A alone closes every High-severity correctness bug and the worst stopwatch defect.
